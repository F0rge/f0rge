1. Executive summary

A tenant is an organisation, not a store. Reuse Firstout’s teams table. Locations such as Kramerville and Bedfordview stay branches inside that organisation.

Isolation is a shared Postgres database plus team_id plus FORCE row-level security. Application filters stay; RLS is the safety net after explicit operator activation. Default single-home compatibility does not claim database isolation. Tenant context is set only after a verified membership is known. Which Postgres GUC style to use (transaction-local vs session-scoped) is chosen by passing pool-lifecycle and commit/refresh tests — not by defaulting to session-scoped settings.

Login moves to Clerk, with Clerk Organisations as tenants. Leo does not want Firstout to handle passwords. Clerk owns sign-in, sessions, memberships, and the organisation switcher. Signed Clerk session claims carry the active organisation id, which maps to the local teams row. Firstout’s fine-grained permission catalogue stays authoritative so no current grant is dropped.

Current access is preserved with a staged dual-auth transition. Existing firstout_session cookies keep working. Users are inventoried first, then imported into Clerk with bcrypt password digests where Clerk accepts them. There is no email-only automatic linking and no forced password reset. A Clerk roster is not proof that people can sign in — that needs real sign-in evidence.

Railway Pro is the chosen plan. Keep the existing frontend hosts and add both app.firstout.co.za and *.app.firstout.co.za with Railway’s wildcard certificate. Hostnames are resolved from a trusted forwarded host, checked against an exact suffix and a strict slug, and must match the signed Clerk organisation (or, for a legacy session, that user’s original team). The Host header is never authorisation by itself. No extra paid add-on beyond Railway Pro without a fresh yes. Billing is built behind a flag and test mode only until the merchant of record is chosen.

3. Tenant shape: organisation, then locations

A tenant is an organisation (the existing teams row). Stores and warehouses are locations. That scales to a second showroom without splitting stock, books, or users. Clerk Organisations map 1:1 onto those teams. Users may belong to several organisations; memberships and roles live per organisation, and the Clerk OrganizationSwitcher (plus a matching local membership) is how they change shop.

4. Isolation options

Under ten tenants in year one, so operational cost and migration risk matter more than theoretical isolation theatre. These are the four realistic options:

OptionHow it worksVerdict for Firstout
Shared database, team_id only Add a column and remember to filter in every query. Too easy to leak. One missed .where(team_id=…) (or a raw SQL helper) exposes another shop. Not enough by itself.
Shared database, team_id + FORCE RLS Same column, plus Postgres policies USING (team_id = current_setting('app.tenant_id', true)::uuid) so even a buggy query returns nothing. Application filters stay as defence in depth. Recommended. Fits the existing one-database Railway service, 78-migration history, and shared types. Needs careful GUC lifecycle (see §9).
Schema per tenant tenant_acme.skus, search_path switching, N copies of every migration. Heavy for fewer than ten tenants and for Alembic 001–078. Cross-tenant reporting and support become painful. Reject for year one.
Database per tenant Separate Postgres (or extra Railway Postgres plugins) and connection routing. Cost and ops grow linearly. Would be a new paid Railway resource without a fresh yes. Reject for year one.

Extend f0rge_db with an organisation-scoped helper rather than misusing enable_tenant_isolation, which hard-codes a user_id column for Marrow. Do not put Firstout domain types in the shared library. Policies should read app.tenant_id, not app.user_id.

5. Clerk auth and Organisations

Leo’s preference (6 Nov, via Chief of Staff): he does not want Firstout handling passwords and logins. Clerk is already connected for the workspace. “Add both to the design” means Clerk and the Railway Pro wildcard — not Cloudflare Access, which was considered and rejected for customer login.

What Clerk owns

  • Sign-up, sign-in, password storage, reset, optional social login and 2FA.
  • Clerk Organisations: one Organisation per Firstout team. Memberships, invitations, and the built-in OrganizationSwitcher (with hidePersonal).
  • The signed session token. When an Organisation is active, Clerk already exposes orgId, orgSlug, and orgRole (Next.js auth() / useAuth()). Customize the session token if needed so FastAPI also receives org_id, org_slug, and the Firstout user id stored as Clerk external_id.

What Firstout still owns

  • The permission catalogue and has_permission checks (catalogue.mutate, till.sell, and the rest).
  • Custom roles created in-app, default locations, disabled flags, document sequences, settings, and all shop data.
  • The trade portal cookie firstout_customer_session. That is a customer login, not staff Organisations. It stays as it is in this design so trade customers are not accidentally locked out. Moving it to Clerk later would be a separate yes.

Recommended Clerk configuration

  • Enable Organisations. Prefer Membership required so staff always have an active org after sign-in (Clerk’s choose-organization session task). Use OrganizationSwitcher with hidePersonal and afterSelectOrganizationUrl pointing at https://:slug.app.firstout.co.za.
  • Disable frontend org creation for imported members (createOrganizationEnabled: false). New tenants are created through Firstout’s signup/provisioning path, which calls Clerk’s Backend API.
  • Next.js 16: @clerk/nextjs, ClerkProvider inside <body>, and proxy.ts (not the older middleware.ts name). Appearance should follow Carbon, not shadcn / @f0rge/ui.
  • FastAPI verifies the Clerk session JWT against Clerk’s JWKS. Do not invent a second session store. During dual-auth it also still accepts a valid firstout_session.
  • Webhooks on a public API route (for example POST /api/v1/webhooks/clerk), verified with Clerk/Svix (verifyWebhook / signing secret). Handle user.*, organization.*, and organizationMembership.*. Use svix-id as an idempotency key. Webhooks are eventually consistent — do not use them as the synchronous source of truth for the request that just signed in; read the session token or call the Backend API instead.
  • API calls from the browser should send a fresh Clerk token from getToken() in the Authorization header. Clerk documents that the session cookie is a singleton and can disagree with the active organisation in another tab.

Roles: Clerk coarse map, Firstout fine grants

Clerk default roles are only org:admin and org:member. Custom roles (up to 10 per instance) can mirror the five presets: org:owner or org:admin ↔ owner, plus org:buyer, org:warehouse, org:till, org:books. Firstout custom roles that do not fit that list stay stored locally; their Clerk membership can use org:member plus the local role id.

Do not replace has_permission with Clerk has() Clerk’s has({ permission }) is for Clerk’s own System Permissions (org:sys_memberships:manage, and so on) and any custom Clerk permissions you create. Firstout already has a richer catalogue. If Clerk Billing were later turned on, Clerk would gate custom permissions by plan features and could suddenly return false. Keep shop authorisation on Firstout’s roles / role_permissions. Map Clerk org roles onto those slugs for new invites, but never reduce a pre-existing user’s permission keys to match a coarser Clerk default.

6. Keeping current access

Leo: “Do not remove any users current access.” That is a hard constraint, not a hope.

1. Inventory first

Before any import or schema cut, snapshot every staff user: id, email, display name, role slug, exact permission keys, is_disabled, token_version, default_location_id, team_id, and team name. Store that snapshot as a migration artefact (no passwords in it). This is the rollback reference for grants.

2. Dual-auth (trickle migration)

Clerk’s own migration guide describes export/import versus a trickle migration that keeps both systems running. Firstout uses trickle:

  • FastAPI accepts a valid firstout_session or a valid Clerk session.
  • Existing cookies are not revoked by the Clerk rollout. Clerk notes that switching session systems “will likely end” old sessions unless you handle that on purpose — we handle it by leaving the current cookie path in place until cutover criteria are met.
  • Unmigrated users keep using email + password against Firstout, including the existing forgot-password flow.
  • Once a user has a linked Clerk identity and has actually signed in with Clerk, new logins prefer Clerk. The old cookie still works until it expires or the user signs out.
  • Do not turn off custom login until the evidence bar in §6.5 is met.

3. Import passwords the supported way

Firstout hashes with bcrypt (bcrypt.hashpw in app/services/auth.py). Clerk’s Backend API CreateUser accepts password_digest plus password_hasher: "bcrypt", and can store the Firstout user UUID as external_id. See Clerk: Migrating and the CreateUser reference. CreateUser is rate-limited; import with backoff.

Disabled users are imported as locked or banned in Clerk so they do not gain a working login. The storefront system actor, if present, is not given a staff Clerk login.

4. Linking rules (safe only)

  • Allowed: create the Clerk user with that person’s imported bcrypt digest and external_id, then store users.clerk_user_id.
  • Allowed: link later if the person completes a Clerk sign-in whose email Clerk has verified, and that verified email matches exactly one Firstout user who is not already linked.
  • Forbidden: automatically linking a Clerk account to a Firstout user only because the email strings match, without a verified Clerk identity or a successful hash import.
  • Forbidden: forcing a password reset as the migration path.
  • Forbidden: emailing everyone a “set your password” link as the default.

If hash import fails for someone (unsupported hash prefix, empty hash, Clerk API error), they keep Firstout login. They are not locked out to “fix” the import.

5. Roster checks are not sign-in proof

Evidence bar “N users exist in Clerk” or “N rows have clerk_user_id set” does not prove anyone can still sign in. Production cutover of custom login requires real sign-in evidence for pre-existing active staff: at least the owner and each distinct live role (till, books, warehouse, buyer, and any custom role actually in use), using the same password they already have or another verified Clerk factor they completed themselves. Automated tests may prove the bcrypt-import mechanism with fixture users; they do not stand in for those live sign-ins. Record who signed in, when (Europe/Luxembourg), and which path (legacy cookie, Clerk with imported hash, or verified-email link).

7. How existing sessions do not open other tenants

Today’s JWT has no tenant claim. After backfill, every current user has exactly one original membership — the existing “Firstout” team. A still-valid firstout_session is bound to that membership only:

  • Resolve the user from sub + ver as today (disabled users and version mismatches still fail).
  • Set tenant context from the user’s legacy home membership (the backfilled original team_id), never from the Host header, never from a query parameter, and never from “any membership this email might later gain.”
  • If the request’s validated host slug is present and does not belong to that home team, reject the request (404/403). Do not silently serve another tenant’s data, and do not “helpfully” switch the legacy session over.
  • Switching tenants is allowed only with a signed Clerk session whose org_id is an organisation the user is a member of. That issues a new Clerk token via OrganizationSwitcher / getToken(). A legacy cookie cannot switch.
  • RLS still applies. A missing tenant filter is contained once FORCE RLS is on, the runtime is non-owner NOBYPASSRLS, and the GUC identifies the authenticated home (or mapped Clerk org). Mutable GUCs do not protect against arbitrary SQL or compromised database credentials.

So a legitimate old session keeps working for the shop that user already uses. Changing the hostname to acme.app.firstout.co.za while holding that cookie does not open Acme.

8. Tenant context and Host checks

Trusted forwarded host

The staff UI talks same-origin to {slug}.app.firstout.co.za/api/…. Next rewrites that to API_URL (today api.firstout.co.za). A naive rewrite makes the API see Host: api.firstout.co.za, so the API cannot read the tenant from its own Host header.

The Next server must copy the incoming browser host — after validating it — into a hop-by-hop header such as X-Firstout-Frontend-Host. Only the Next server sets that header, overwriting any client-supplied value. The API:

  • Does not treat that header as proof of tenancy.
  • Accepts it only as the hostname to compare against the already-authorised team slug.
  • If someone spoofs acme.app… while their Clerk org is Beta, the check fails. Spoofing cannot grant access.
  • If the header is absent (Swagger, bearer scripts), skip the host comparison and rely solely on the signed org / legacy home team.

Validation of any host value, whether from the frontend request or a forwarded header:

  • Configure trusted proxy behaviour explicitly (Railway’s X-Forwarded-Host / X-Forwarded-Proto). Do not trust forwarded host headers from arbitrary clients on a directly reachable API.
  • Allow only: firstout.co.za, www.firstout.co.za, app.firstout.co.za, or {slug}.app.firstout.co.za.
  • Slug: lowercase DNS label, ^[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?$, compared as a full string equality to {slug}.app.firstout.co.za. Reject suffix tricks such as app.firstout.co.za.evil.com or extra dots.
  • Reserved slugs: www, api, app, admin, mail, status, support, billing, signup, login, static, cdn, trade.

9. Pitfalls

Connection pooling and tenant GUCs

f0rge_db currently uses session-scoped set_config('app.user_id', …, false) because transaction-local settings are cleared on COMMIT and that broke refresh() after writes. It also re-applies the GUC on SQLAlchemy after_begin, and RESETs on the way back to the pool.

Do not default to session-scoped tenant settings Session-scoped GUCs leak to the next request if RESET is skipped, which is especially dangerous with a pooler. Implementation must run a matrix before choosing a mechanism:
  1. Write, commit, then refresh() still sees the row.
  2. A connection used for tenant A, returned to the pool, then used for tenant B, cannot see A’s GUC or A’s rows.
  3. A failed/aborted transaction does not poison the next request on that connection.
  4. If both DATABASE_URL and DIRECT_DATABASE_URL are in play, test the URL the API will actually use. Do not print those values.

Pick the option that passes. If transaction-local SET LOCAL (or set_config(..., true)) plus the existing after_begin re-apply passes commit/refresh and the pool tests, prefer it. Session-scoped settings are acceptable only with the same pool tests passing and RESET covered on every session factory (request get_db, Cin7 _run_detached, payment-reminder ticker, CLI import).

Migrations, owners, support

FORCE RLS; the app role must not be table owner and must not have BYPASSRLS. Cross-tenant backfills use f0rge_db.rls.migration_bypass. Support access is an explicit impersonation path with an audit row, not a connection as table owner. Verify the live role setup before forcing RLS — it was not queried in the research pass. Alembic prepares policies only; the separately invoked cutover activates them after role and proxy readiness checks. See the staged deployment runbook.

Background jobs

Payment reminders, Cin7 detached jobs, CLI import, and the WhatsApp webhook must set tenant context from the job or phone-number mapping, never from leftover GUCs. Cin7’s global one-job lock becomes one active job per team. Storage keys move under tenants/{team_id}/….

Clerk webhooks vs access

During dual-auth, user.deleted or organizationMembership.deleted must not strip a pre-existing user’s local access. Sync the Clerk link; do not delete the Firstout user or their home membership to “match Clerk.” After cutover, document a separate policy for intentional removals.

Unique constraints and IDs

Most Firstout tables today are globally unique with no team_id. After backfill they become unique per team. At minimum rewrite uniqueness for:

  • SKU our_ref and barcodes
  • Location names (and any other location unique keys)
  • Customer display names / trade identifiers as they are unique today
  • Role slugs per team (presets are cloned or scoped, not shared across shops)
  • Document numbers (invoices, quotes, and similar) — document_sequences is already per team
  • Account codes and other books unique keys
  • Trade-portal customer emails if they are globally unique today
  • Cin7 “one active import” lock: one active job per team, not one globally

Primary keys stay UUIDs, so id-based URLs do not become guessable across tenants; isolation tests must still treat a foreign UUID as 404, not 403 with a leaky body.

Notable paths for implementers: apps/firstout/backend/app/services/auth.py (bcrypt, JWT), app/permissions.py, auth middleware, models for team/user/role/team_settings/document_sequence/location/sku/customer/cin7_import_run, database.py register_rls_hook, Cin7 jobs and storage prefix cin7-imports/{id}.zip, Next next.config.ts rewrite of /api to API_URL, frontend sku-label-print.ts, print-bin-labels.ts, print-html.ts.

No extra paid add-on

Railway Pro is approved. Do not buy Cloudflare Advanced Certificate Manager, Clerk plan upgrades, or other add-ons without a fresh yes. Prefer DNS-only (grey cloud) for the nested wildcard so Railway can issue the certificate without Cloudflare ACM. If Clerk Organisations or custom roles turn out to require a paid Clerk plan beyond what is already connected, stop and report rather than upgrading.

10. Target architecture

  • One Railway project, one API, one frontend, one Postgres, one bucket — same services as today.
  • https://firstout.co.za and www.firstout.co.za — marketing, signup entry, legacy host for the original shop during migration.
  • https://app.firstout.co.za — Clerk primary (sign-in, choose-organisation). A wildcard does not cover this parent name, so it is a separate custom domain.
  • https://{slug}.app.firstout.co.za — tenant back office. New slugs need no per-tenant DNS.
  • https://api.firstout.co.za — API, webhooks, Swagger. Unchanged hostname, different service from the frontend wildcard (Railway overlap rule).
  • Reserved admin.app.firstout.co.za if platform support UI is built later.
  • Trade portal remains /trade/… on the tenant host, still using firstout_customer_session.
  • Legacy firstout_session remains host-only. Clerk manages its own cookies; no custom .app.firstout.co.za cookie-domain configuration was applied. Restrict Clerk origins to the approved hosts. This is the historical architecture document; see the current release evidence for deployed state and remaining gates.

12. Data backfill and database safety

  1. Backup. Take a full Postgres backup of the live Firstout database before any multi-tenant migration. Restore that backup onto a disposable instance and confirm the app can start against it. A file that was never restored is not a rollback plan.
  2. Inventory users and roles (see §6). Confirm no unexpected extra teams.
  3. Add slug/status/clerk_org_id on teams. Backfill the existing “Firstout” team as slug firstout, status active.
  4. Create memberships from current users.team_id, role, permissions, default location, and disabled flag. Mark each as is_legacy_home. No role is rewritten.
  5. Add nullable team_id to tenant-owned tables, backfill from that single team, then NOT NULL. Rewrite global unique indexes to (team_id, …). New Alembic revisions after 078_password_reset — do not edit already-applied files.
  6. Import users into Clerk with bcrypt digests and external_id. Create the matching Clerk Organisation and memberships. Link ids locally. Failures leave Firstout login intact.
  7. Turn on dual-auth. Only later, after sign-in evidence, stop issuing new firstout_session cookies. Keep accepting old ones until they expire.
  8. Enable FORCE RLS only after the app and every worker always set tenant context, and after isolation tests pass against a non-bypass role. This step must be separately reversible.

Rollback: restore the tested backup if a migration or import goes wrong. Down-migrations are optional extra safety and are not a substitute for a tested restore. Cross-tenant SQL inside migrations uses migration_bypass.

13. Subdomains, DNS and TLS

Railway supports wildcard custom domains (Working with domains). A subdomain and a wildcard cannot overlap across services (Specs & limits), so the wildcard cannot be *.firstout.co.za while api.firstout.co.za lives on firstout-api.

Railway Pro — chosen Leo added a Pro subscription (6 Nov 17:45). Hobby’s two-domain cap no longer applies to this design (Pro allows 20 custom domains per service by default). Keep firstout.co.za and www.firstout.co.za, and add both app.firstout.co.za and *.app.firstout.co.za on firstout-frontend. Railway issues the wildcard certificate when the wildcard CNAME, _acme-challenge CNAME, and TXT record are all present.

New tenant slugs need no Cloudflare or Railway change. The app stores the slug; unknown slugs 404.

  • Cloudflare: keep _acme-challenge DNS-only. Prefer DNS-only for *.app.firstout.co.za as well, so Railway’s Let’s Encrypt wildcard certificate is used and Cloudflare Advanced Certificate Manager (a paid add-on) is not required.
  • Existing apex/www proxy settings can stay as they are if they already work (Railway asked for SSL/TLS Full when orange-clouded).
  • Custom hostnames such as stock.acme.com (Cloudflare for SaaS) are out of scope and may involve extra cost — not in this build.

14. Signup and billing

Self-serve signup can still create a Clerk user, a Clerk Organisation, a local team, cloned role presets, and empty locations (not a copy of Kramerville/Bedfordview).

No live charges yet The merchant of record is still undecided (Stripe if F0rge bills from a Stripe country such as Luxembourg; Paystack if a South African company bills — see Stripe’s global page routing ZA to Paystack). 15. Branding storage

Unchanged: team_settings already has legal and trading names, address, VAT, bank lines, and a logo. Password-reset and outbound mail for unmigrated users still use the shop mailbox; after Clerk cutover, Clerk sends login mail. PDF logos stay on Firstout settings. Do not put tenant CSS in libs/ui.

16. Tag and label printing

Unchanged: Firstout prints SKU and bin labels in the browser (sku-label-print.ts, print-bin-labels.ts, print-html.ts). Per-tenant setup is label size and which fields/logo to show, stored on team_settings. Do not route tenants through DasKasas (apps/dk/tag-printer, no auth, no database).

17. Testing and security checks

  • All previous isolation tests: two tenants, same our_ref / invoice number; UUID IDOR returns 404; raw SQL without a GUC sees nothing; WITH CHECK blocks cross-tenant inserts; Cin7 and reminders stay inside one team.
  • GUC pool-lifecycle and commit/refresh matrix (§9).
  • Legacy session cannot read a second tenant by changing Host or the forwarded-host header.
  • Clerk session for org A rejected on host B; getToken() org matches membership.
  • Host parser rejects malformed suffixes and reserved slugs.
  • Permission snapshot: after backfill, every inventoried user still has the same permission keys (automated comparison against the snapshot).
  • Bcrypt import fixture: a test user whose digest was imported into a Clerk test instance (or Clerk’s documented hasher test) can sign in without a reset. This proves the mechanism, not production staff access.
  • Disabled users cannot sign in via Clerk or Firstout.
  • Webhook signature failures return 400; forged membership deletions during dual-auth do not strip local home memberships.

19. Risks

  • Claiming import success without live sign-in evidence.
  • Email-only linking, or a forced reset, locking people out or attaching the wrong identity.
  • Replacing Firstout permissions with Clerk defaults and silently dropping grants.
  • Trusting Host or X-Forwarded-Host as authorisation, or forgetting that Next rewrites hide the browser Host from the API.
  • Session-scoped GUCs leaking across a pool.
  • Webhook handlers deleting local access during dual-auth.
  • Clerk plan limits (custom roles, Organisations, MRU) appearing only at implementation time — stop rather than purchase.
  • Turning on live billing before a merchant of record is chosen.
  • Breaking the trade portal by folding it into Clerk Organisations without a separate design.
