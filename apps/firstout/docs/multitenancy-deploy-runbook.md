## Schema preparation and explicit RLS activation

Revisions 079/080 preserve home identity/grants and backfill business ownership, scoped keys and tenant foreign keys; 081 prepares business-table policies; 082 adds tenant invitation storage and its policy. Revision 080 changes row-ownership columns, not PostgreSQL table owners. Revisions 079–082 have now been applied to production. Routine Alembic execution does not activate/deactivate RLS; explicit operator cutover does. Do not stamp an environment-conditioned no-op as an applied security migration.

The code's default `single_home` mode is for pre-cutover compatibility with exactly the original home, legacy login and no Clerk/signup/import. It logs that database tenant isolation is not enforced and refuses extra teams or already-active tenant RLS. It does not describe the current multi-tenant production mode. `COOKIE_SECURE` selects cookie transport only, not isolation.

For an initial cutover on a separately rehearsed single-home installation:

1. Provision a dedicated LOGIN runtime role: NOSUPERUSER, NOBYPASSRLS, owns no application table and has no owner/superuser/bypass membership. Grant required schema/DML/sequence privileges. Keep a separate migration/operator owner URL.
2. Verify both URLs identify the same intended database/topology and exercise actual grants. Identity-directory tables remain application-scoped, with narrow pre-authentication lookups; do not describe their grants as business-table RLS.
3. Configure the same server-only `FRONTEND_PROXY_SECRET` on Next/API, keep Clerk/signup/import OFF, and prepare `TENANT_ISOLATION_MODE=enforced`. Next strips supplied forwarding headers and signs the normalized frontend Host with HMAC-SHA256. The signature authenticates the Host assertion, not user identity. A one-sided secret change can fail serving requests.
4. Stop traffic and relevant background work for the cutover. Never run the compatibility owner-credential API concurrently with multi-tenant activation. In the restricted operator environment, with runtime `DATABASE_URL`, owner `MIGRATION_DATABASE_URL`, enforced mode and the proxy secret, run:

   ```bash
   cd apps/firstout/backend
   uv run python -m app.commands.tenant_cutover activate
   ```

5. The command checks runtime role/ownership/grants, endpoint identity and canonical policies before transactional activation. It commits, then verifies through the runtime connection. A pre-commit failure rolls back activation; a post-commit verification failure leaves RLS active until inspected. Never assume rollback occurred.
6. Restart using only the verified restricted runtime and enforced mode. Startup must verify canonical ENABLE + FORCE policies and proxy configuration. Verify health, retained login/cookies, wrong-host rejection and tenant-specific reads before resuming traffic. Enabling Clerk/provisioning is a later release gate.

The 2026-11-08 production cutover followed this stopped-traffic boundary; its temporary strict loopback-only SSH tunnel was closed afterward. Additional tenants now exist: **do not use compatibility deactivation in the current production database.**

### Isolation limits

Mutable `app.tenant_id` RLS protects against missing application filters and foreign-UUID mistakes under the restricted runtime. Composite foreign keys prevent cross-tenant references; transaction-local context and pool cleanup prevent leakage between requests. It does not protect arbitrary SQL execution, compromised credentials able to set another tenant context, superusers, bypass roles or owners able to change policies. It is not SQL-injection immunity. Directory identities/memberships are application-scoped rather than covered by business-table RLS.

## Rollback and release evidence

Stop rollout on lost staff access/grants, cross-tenant reads/writes, missing assets, invalid runtime role or unexplained migration differences. Close new signup entry points and pause relevant jobs while retaining legacy access. Preserve imported identities, hashes, token versions and memberships. Revert to a recorded schema-compatible application revision/image only after checking compatibility.

Before any additional tenant exists, a separately approved, rehearsed rollback can stop traffic/jobs, set single-home mode and Clerk/signup/import OFF, and run `uv run python -m app.commands.tenant_cutover deactivate` using the owner boundary. It must refuse anything other than the original home. **This path is forbidden now that additional production tenants exist.** Keep enforced isolation and repair or restore to an isolated replacement; disabling RLS is never a leak workaround.

For destructive failures, halt writes, restore the tested encrypted snapshot into an isolated replacement, compare staff/document inventories and sign-ins, then perform a separately approved connection cutover. Retain the failed database for investigation. Scoped uniqueness can prevent downgrade once tenants share natural keys; never delete conflicting rows to force a downgrade. Same-volume snapshot retention is not independent disaster recovery.

Record source/CI/image/deployment status, runtime manifest comparison, restore evidence, baseline staff preservation, all 82 RLS policies, actual hosted checks, and every pending limitation in the [release evidence](multitenancy-release-evidence-20261108.md). Final QA results must update that record before any completion claim. Historical synthetic results, healthy deployment, matching source and successful import are distinct evidence and do not substitute for one another.
