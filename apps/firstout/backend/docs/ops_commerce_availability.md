# Ops Commerce availability contract (v1)

`GET /api/v1/ops-commerce/v1/products` reports each published SKU's `available_quantity` as nonnegative physical on-hand stock across Ops locations. A staff sales-order hold already posts an outgoing stock movement, so the feed does not subtract `held_qty` again.

Till reservations (open baskets, held sales and invoice-held lines in `stock_reservations`) have not deducted stock yet, so the feed does subtract them: `available_quantity = max(0, floor(non-negative on-hand) - live reservations of every holder)`. Expired reservations (`expires_at` in the past) are not subtracted, even before they are pruned. A reservation is always deleted in the same transaction that deducts its stock, so a unit is never counted both ways.

Each product has a fixed-width UTC `revision` (`YYYY-MM-DDTHH:MM:SS.ffffffZ`) and UTC `observed_at`. `revision` is the greatest of the SKU, stock, merchandising and acknowledgement change times and the SKU's reservation change time, so an idle SKU keeps a stable revision between polls. A release, move, creation or prune of a reservation row writes `stock_reservation_changes(team_id, sku_id, changed_at)` through a database trigger on `stock_reservations`, so no code path can change a reservation without bumping the revision. Lazy expiry changes no row, so an expired but not yet pruned reservation contributes its `expires_at` to the revision instead; once pruned, the trigger's mark takes over and the revision never goes backwards. The commerce adapter retains the greatest applied revision for each source SKU and applies stock changes only for newer snapshots. An equal revision can refresh `observed_at` without changing stock. `observed_at` is the time of the read, not a stock version.

`acknowledged_commitment_ids` is a sorted list of opaque, globally unique channel **line** IDs whose quantities have already been deducted from operational stock. The IDs are durable in `ops_commerce_acknowledgements`, with source SKU and positive quantity. There is no public acknowledgement mutation in this phase. A later paid-order importer must write the outgoing stock movement and acknowledgement in one transaction, idempotently by `commitment_id`. It must never write an acknowledgement without the stock movement.

Commerce computes effective available stock by subtracting only paid channel commitments whose IDs are absent from `acknowledged_commitment_ids` from the Ops `available_quantity`. It must retain those pending commitments across polls and restarts, including when an older Ops snapshot arrives. Once a newer snapshot includes an ID, its stock movement is already reflected in `available_quantity`, so commerce stops subtracting that commitment. A failed or unknown availability feed must be treated as stale at checkout; the storefront's freshness threshold and hold TTL are separate channel settings.

The commerce adapter reads pending commitments from each Medusa variant's `pending_paid_commitments` metadata on every sync, including when the source revision is unchanged. The paid-order importer in a later phase owns writing this durable list and immediately projecting its own commitment under the inventory lock. Missing metadata means no paid commitments yet; malformed or duplicate entries fail the sync instead of silently raising sellable stock.

## Which SKUs are in the feed

With `OPS_COMMERCE_AUTO_PUBLISH_ENABLED` off (the default), the feed is selected by the hand-set `storefront_published` flags, as before, and carries no `shop_category`.

With it on, the rule applies to every SKU, grouped or not: a SKU is in the feed when its category maps to a shop category, it has a photo (`photo_storage_key` set) and `storefront_hidden` is false; it must still be sellable, unarchived and priced. `storefront_published` is ignored. Categories match trimmed and in any case: Sofas and Armchairs → `sofas-armchairs`; Dining Room → `dining-room`; Bedroom → `bedroom`; Coffee and Lamp Tables and Consoles and TV Units → `coffee-console-tables`. The mapping is `SHOP_CATEGORIES` in `app/crud/ops_commerce.py`; the database alone matches categories against it (one SQL `CASE`), so a row is either mapped or left out, never sent with a null category. Each product carries `shop_category`, one of those four handles. A product group appears with only its qualifying members, and is left out entirely while any member is archived, unsellable or unpriced. If its qualifying members map to different shop categories, all of them carry the category of the first by SKU code. Whether a piece is then on sale (stock or a live made-to-order offer) is decided in commerce.

Staff hide a SKU with `PATCH /api/v1/skus/{id}` `{"storefront_hidden": true}`, which needs `catalogue.mutate`; `storefront_hidden` is on `SkuResponse` (SKU list, get, create and update).

Go-live: the key is omitted while the setting is off because the commerce contract is strict. Once both the Firstout and DasKasas releases carrying auto-publish are live, set `OPS_COMMERCE_AUTO_PUBLISH_ENABLED=true` on `firstout-api` and redeploy it. Auto-publish needs photos, so with it on the feed also sends `photo_token`, whatever `OPS_COMMERCE_PHOTO_TOKENS_ENABLED` says. Pieces published by hand that fail the rule leave the feed and commerce withdraws them. With it on, `storefront_published` no longer blocks archiving a SKU; an archived SKU leaves the feed.

Rollback: turn `OPS_COMMERCE_AUTO_PUBLISH_ENABLED` off before rolling commerce back to a pre-#1018 image, which rejects `shop_category` and pauses checkout.

## Product photos

`photo_token` is in the feed only when `OPS_COMMERCE_PHOTO_TOKENS_ENABLED=true` (default off). When off, the key is omitted, not null, because a storefront commerce release older than the photo sync has a strict contract that rejects unknown keys and would stop its sync. Go-live: once both the Firstout and DasKasas releases carrying the photo sync are live, set `OPS_COMMERCE_PHOTO_TOKENS_ENABLED=true` on the `firstout-api` service in Firstout's Railway project and redeploy that service. The photo route below is available either way.

When enabled, each product carries `photo_token`: the SHA-256 of the SKU's photo storage key, or null when the SKU has no photo. A SKU photo is write-once (upload refuses to overwrite its key and nothing clears it), so the key identifies the bytes and the token changes only when the photo does. The feed never reads photo bytes. A future replace action must store the new photo under a new key so the token changes.

`GET /api/v1/ops-commerce/v1/products/{source_sku_id}/photo` returns that photo as `image/jpeg`. It uses the same bearer token, allowed host and `X-Ops-Company-ID` checks as the feed, so it is tenant-scoped. It returns 404 for a SKU that is not in the feed, belongs to another company, or has no photo. There is no public route and no presigned URL; the bucket stays private.

For a reviewed gallery, the version 2 feed carries three ordered studio checksums in `gallery_photo_tokens`. With `catalogue_version=2&include_setting_photo=true`, each SKU also carries `setting_photo_token`, the SHA-256 of its retained setting JPEG or `null` if it has none. Consumers fetch the ordered studio JPEGs with `?slot=1` through `?slot=3` and the separate setting with `?slot=4`. All slots use the same feed eligibility and authorization.

An organisation owner can choose **Single SKU** on the catalogue import page to update an already selected storefront SKU. The ZIP uses the reviewed catalogue manifest format with one SKU, three studio photos and an empty groups list. With `retain_current_photo_as_setting: true` on that SKU, Firstout preserves the existing JPEG bytes in slot 4. Preview validates the archive and reports the number of gallery photos. Apply leaves other SKUs and variant groups in their current selection.
